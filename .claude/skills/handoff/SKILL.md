# 引き継ぎ資料の更新

`docs/handoff.md` は、新しいセッションの Claude が最初に読む資料。読んだ Claude が「何が決まっていて、今どこにいて、次に何をするか」を、この会話を見なくても分かる状態にするのが目的。

## 手順

### 1. 今の資料を読む

`docs/handoff.md` を読む。ファイルがなければ、末尾の「資料の構成」に沿って新しく作る。

### 2. リポジトリの事実を集める

推測で書かず、コマンドで確かめる。

```bash
git branch --show-current
git status --short
git log --oneline -10
git log --oneline main..HEAD   # main にまだマージしていないコミット
```

構成を書き換えるときは、`ls` などで実際のフォルダ構成も確かめる。

### 3. 会話から更新内容を拾う

前回の更新以降の会話を振り返り、次のものを拾う。

- 新しく決めたことと、その理由（選ばなかった案も）
- 終わったステップと、次に取りかかるステップ
- レビューで指摘したが、まだ直していない点。前回の資料にあって、もう直ったものは消す
- つまずいたことと、その解決方法・回避方法
- ユーザーとの進め方について、新しく合意したこと

### 4. 資料を更新する

- 冒頭の「最終更新」の日付を今日にする
- 「現在の状態」は全体を書き直す。古い状態を残さない
- 「今後の手順」は、終わったステップに「完了」と書き、「← 次はここから」の印を次のステップに移す
- 「決めたこと」と「ハマりどころ」は追記する。前の内容が間違いだったと分かったものは直す

### 5. 他の資料への反映を提案する

handoff.md だけを直して終わりにしない。次に当てはまるものがあれば、ユーザーに提案する。勝手には直さない。

- 要件や技術の決定が変わった → `docs/requirements.md` や `docs/tech-stack.md` の更新を提案する
- 進め方のルールが変わった → `CLAUDE.md` の更新を提案する

### 6. ユーザーに報告する

何を更新したかを箇条書きで短く伝える。資料の全文は貼らない。

## 守ること

- **確かめていないことは書かない。** 動作確認していないものを「動く」と書かない。分からないことは「未確認」と書く
- **会話の経緯は書かない。** 書くのは結果・理由・現状だけにする
- **コミットしない。** `docs/handoff.md` は `.gitignore` に入っているローカル専用の資料
- **Claude のメモリには書かない。** メモリへの書き込みには、ユーザーの事前の承認が必要
- 日本語で、短い文で書く

## 資料の構成

新しく作るときは、この章立てにする。既存の資料もこの構成を保つ。

1. **プロジェクト概要**：アプリの目的と、`docs/` 配下の各資料の役割
2. **進め方の約束**：コードを書くのは誰か、レビューの仕方、Git の運用
3. **これまでに決めたこと**：要件と技術の要点、選んだ理由、選ばなかった案
4. **現在の状態**：ブランチ、最新のコミット、フォルダ構成、動く部分、起動方法、まだ直していないレビューの指摘
5. **今後の手順**：ステップの一覧（完了と次の印つき）、順番の理由、次のステップの細かい進め方
6. **環境とハマりどころ**：ローカル環境のバージョンと、つまずいた点・回避方法
